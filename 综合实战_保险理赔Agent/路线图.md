# 分阶段实现路线图 · 保险理赔智能审核 Agent

> 配合 [`README.md`](./README.md)（需求文档）使用。
> **不知道每步具体做什么时，看 [`开发实操手册.md`](./开发实操手册.md)**——它把本路线图展开成可勾选的步骤清单和自测命令。
> **原则**：每个 Phase 都是一个"能独立自测通过的里程碑"，严格按依赖顺序推进；上一阶段自测不过，不进下一阶段。
> 每个 Phase 给出：**目标 / 前置依赖 / 要写的文件 / 关键点 / 自测方法 / 复习点**。
> 代码你来写；每写完一个 Phase，我们对照"自测方法"验证通过再进下一个。

## Phase 0 · 环境与依赖打底

**目标**：把 Milvus、Postgres、模型、embedding 四条腿都能连通。

**要做**
- 依赖：`uv add pymilvus`（Milvus 客户端）。
- 起 Milvus：本地 `docker` 起 standalone，或用 Zilliz Cloud；拿到 `MILVUS_URI`（本地形如 `http://localhost:19530`）。
- 起 Postgres：复用你项目已有的 `DB_URI`（Neon/本地皆可）。
- `.env` 增：`MILVUS_URI`、`MILVUS_TOKEN`（本地无鉴权可留空）。
- 确认复用 `provider.glm_model`（GLM）与 `provider.embeddings`（千问 DashScope）可用。

**自测**
- 一段临时脚本：连上 Milvus（`utility.get_server_version` 或 `MilvusClient` 能建/删一个测试 collection）；`embeddings.embed_query("测试")` 返回向量并打印维度（记下维度，建 collection 要用）。

**复习点**：环境/依赖（无新知识，先扫清障碍）。

## Phase 1 · 业务数据层 `data/db.py`

**目标**：`clm_*` 五张表建好 + 灌入 5 个样例案件，幂等。

**前置**：Phase 0。

**要写**：`data/db.py`（SQLAlchemy 2.0 ORM，风格对齐你已有的 `provider/ecommerce.py`）、`data/raw_clauses.py`（条款&历史案例语料，纯 Python 数据，Phase 2 用）。

**关键点**
- 表：`clm_policies / clm_insureds / clm_claims / clm_claim_materials / clm_case_events`（+可选 `clm_fraud_watch`）。字段见 PRD 5.1，每个字段加中文注释。
- 种子严格按 PRD 5.3 造 A~E 五个案件：Case A 数据要能算出应赔 0.8 万、B 算出 12 万、C 落在等待期内/既往症、D 故意缺"费用清单"、E 造出"90 天内 3 次 + 关注名单机构"。
- 幂等：主键存在则跳过（`session.get` + `merge`）。
- 对外查询函数返回纯 `dict`（不泄露 ORM 对象），方便后面节点直接用。

**自测**：`python data/db.py` 打印各表行数 + 5 个样例案件概览；手算校验 A/B 的应赔金额与种子一致。

**复习点**：SQLAlchemy（你已掌握，快速过）。

## Phase 2 · Milvus 知识层 `kb/`

**目标**：条款库、历史案例库两个 collection 建好、灌好、能带过滤检索。

**前置**：Phase 0、Phase 1（语料来自 `data/raw_clauses.py`）。

**要写**
- `kb/milvus_store.py`：连接客户端；`ensure_collection(name, dim, schema)` 建 collection + 建 `HNSW` 索引 + load；通用 `search(name, query_vec, top_k, expr=None)`（`expr` 用于 metadata 过滤）。
- `kb/ingest.py`：读 `raw_clauses.py` → 每条 `embeddings.embed_query` → 组装带元数据的行 → 插入。**幂等**（灌前按业务主键去重，或先 drop 再建的开关）。
- `kb/retriever.py`：`search_clauses(query, product, category=None, top_k=3)`（按险种/类别过滤）、`search_similar_cases(summary, product, top_k=3)`（反欺诈用）。返回结构化结果（text + clause_no/label + score）。

**关键点**
- 维度用 Phase 0 记下的 embedding 维度。
- 度量与归一化一致（用 `COSINE` 最省心）。
- 元数据字段（product/category/clause_no/label）建为 scalar field，检索时用 `expr` 过滤（如 `product == "医疗险" and category == "免赔额"`）。

**自测**
- 灌库后：查"住院费用免赔额怎么算" → top 命中应是免赔额条款；加 `expr` 过滤险种后结果被正确收窄；反欺诈"相似案例"能命中 E 案件对应的历史欺诈案例。

**复习点**：Milvus collection/schema/索引/插入/metadata 过滤检索 —— 一次全过。

## Phase 3 · 状态定义 + 最小骨架图 `core/state.py` `core/graph.py`

**目标**：图能编译、能 `invoke`，先把"立案 → 抽取(桩) → END"跑通。

**前置**：Phase 1。

**要写**
- `core/state.py`：`ClaimState`（claim_id、保单快照、材料列表、抽取结果、校验结果、条款证据、风险、应赔金额、决策、日志等）。给需要累加的字段配 reducer（如事件日志用 `add`/自定义 reducer）。
- `core/graph.py`：`StateGraph(ClaimState)`，先只加 `intake`（立案：读库把案件/保单/材料塞进 state）和一个抽取桩节点，`compile()`。

**自测**：喂 Case A 的 `claim_id`，`invoke` 后 state 里能看到保单快照和材料列表。

**复习点**：StateGraph / reducer。

---

## Phase 4 · 材料抽取（Send 并行）`core/extract.py`

**目标**：一个案件多份材料**并行**抽取，结果 reduce 回 state。

**前置**：Phase 3。

**要写**：`core/extract.py`——一个 fan-out 节点用 `Send` 对每份材料下发一个抽取子任务；抽取节点调 `glm_model` 抽结构化字段（金额/日期/诊断/机构/票据类型）；结果并回 state 的材料抽取列表。

**关键点**
- 用 `Send(node, {单份材料})` 实现 Map；结果字段配好 reducer 做 Reduce。
- 抽取节点包一层**重试/降级**（模型抽取失败给兜底空结构 + 标记异常）——顺带复习容错，也为 Phase 9 打底。

**自测**：Case E（多材料）能看到各材料并行产出抽取结果；人为让一份材料抽取抛错，流程不崩、该材料标记异常。

**复习点**：Send / Map-Reduce（+ 容错雏形）。

---

## Phase 5 · 校验 + 保单核对 + 待补件分支 `core/validate.py` `core/policy_check.py`

**目标**：材料齐全性/一致性校验；缺件走"待补件"，齐全走"保单核对"。

**前置**：Phase 4。

**要写**
- `core/validate.py`：必需材料齐全性 + 一致性（金额/日期/姓名）。
- `core/policy_check.py`：是否在保、过等待期、读免赔额/比例/保额余额/既往症。
- `graph.py` 加条件边：校验不过 → `待补件`（终止或挂起等补件）；过 → `policy_check`。

**自测**：Case D 命中缺件 → 待补件；A/B/C/E 通过校验进入保单核对；Case C 在保单核对识别出"等待期内/既往症"。

**复习点**：条件边、reducer、状态流转。

---

## Phase 6 · 条款匹配 + 反欺诈子图 `core/clause_match.py` `core/fraud.py`

**目标**：并行完成条款匹配与反欺诈初筛。

**前置**：Phase 2（检索）、Phase 5。

**要写**
- `core/clause_match.py`：用诊断+费用类型调 `kb.retriever.search_clauses`，产出适用条款证据（报销比例/免赔/除外/等待期）。
- `core/fraud.py`：**做成独立子图**——内部：规则信号（短期多次/金额异常/名单）+ `search_similar_cases` 相似历史案例 → 汇总风险等级+理由。子图作为一个节点挂进主图。
- `graph.py`：`policy_check` 之后 **并行** 进入 `clause_match` 与 `fraud`（两条边），再汇合到测算。

**自测**：Case E 风险=高（命中名单+相似欺诈案例+多次理赔）；Case A 风险=低；条款匹配对 A 返回免赔额/报销比例条款证据。

**复习点**：子图、（并行）检索、Milvus 过滤检索复用。

---

## Phase 7 · 赔付测算 + 决策路由（Command）`core/settle.py` `core/decide.py`

**目标**：算应赔金额；按规则用 `Command` 三分支路由。

**前置**：Phase 6。

**要写**
- `core/settle.py`：按 PRD 公式算应赔，产出可解释计算明细（每项扣减写清）。
- `core/decide.py`：`Command(goto, update)` 路由——低额低风险齐全→`auto_pay`；大额/高风险/存疑→`human_review`；保单不符→`reject`。
- `graph.py`：加 `auto_pay` / `reject` 出具结论节点（`human_review` 下阶段做）。

**自测**：A→auto_pay(0.8 万)、B→human_review、C→reject(引条款)、E→human_review；每个决策都带可解释理由。

**复习点**：Command(goto+update)、条件路由。

---

## Phase 8 · HITL 人工核赔 + 持久化 `core/human_review.py` + checkpointer

**目标**：转人工案件在核赔节点中断，核赔员裁决后 resume；案件可跨进程恢复。

**前置**：Phase 7。

**要写**
- `core/human_review.py`：`interrupt(...)` 抛出给核赔员的载荷（应赔额/明细/条款/风险/抽取原文）；恢复时读取核赔员动作（通过/驳回/改额/退补），据此更新 state 并路由到 出具结论 / 待补件。
- `graph.py`：`compile(checkpointer=PostgresSaver(...))`；线程键=`claim_id`。

**自测**：Case B 停在核赔（拿到 `__interrupt__` 载荷）；用 `Command(resume=...)` 注入"通过"结案、"改额"改赔付额、"退补"回到待补件；**重启进程**后凭 `claim_id` 能继续。

**复习点**：HITL interrupt/resume、Postgres 持久化。

## Phase 9 · 长期记忆 + 时间旅行 + 容错收尾

**目标**：跨案件记忆被保险人历史；演示审计回溯与抽取容错。

**前置**：Phase 8。

**要做**
- **store**：以 `insured_id` 为键累积历史理赔（次数/金额/结论），`fraud.py` 读它增强"短期多次"判断。
- **时间旅行**：用 `get_state_history` 找到"条款匹配"检查点，从该步 `invoke(None, checkpoint)` 重跑，演示改条款后结论变化。
- **容错**：给抽取节点正式加重试策略/降级兜底（把 Phase 4 的雏形做扎实）。

**自测**：E 案件因历史记忆命中"90 天 3 次"升风险；能从中间检查点重跑得到不同结论；抽取偶发失败可自动重试成功。

**复习点**：store 长期记忆、时间旅行、容错。

> 到此 **`core/app.py` 应能独立跑通 5 个样例案件全部分支，完全不依赖 Langfuse**。这是纯业务层的验收线。

## Phase 10 · 观测层接入 Langfuse `obs/instrumented.py` `obs/pii.py` `obs/client.py`

**目标**：不改业务代码，给整图叠加 trace + session + PII 脱敏。

**前置**：Phase 9。

**要写**
- `obs/_setup.py`：sys.path/.env 准备（对齐你 00_真实业务场景 的分层约定）。
- `obs/pii.py`：身份证/银行卡/手机号/病历敏感字段打码。
- `obs/client.py`：带 mask 钩子的 langfuse client（进程内第一个 client）。
- `obs/instrumented.py`：给 `graph.invoke` 挂 `CallbackHandler`；每案件一个 trace，补件多轮用 `session_id=claim_id` 串联；检索/生成自然成 span/generation。

**自测**：`obs/run.py` 跑 A/B/E 后，UI 看到嵌套 trace（抽取/校验/条款匹配/反欺诈/测算/决策/核赔）；含身份证那份材料显示为脱敏。

**复习点**：trace/span/generation/retriever、session、PII 脱敏。

## Phase 11 · Prompt 托管 + 成本 `obs/prompts.py`

**目标**：抽取/决策/拒赔话术 prompt 托管到 Langfuse；成本可见。

**前置**：Phase 10。

**要做**
- `obs/prompts.py`：把三个 prompt 推送到 Langfuse，业务侧改为拉取托管版本（带本地回退）；演示 label 灰度（`production` vs `latest`）。
- 成本：Langfuse UI 配 `glm-*` 定价（见 00_真实业务场景 README 的定价说明），重跑后 generation 成本非 0。

**自测**：在 UI 改拒赔话术 prompt，重跑 Case C 拒赔说明措辞随之变化，代码不动；trace 上 generation 成本非 0。

**复习点**：Prompt 托管 + label 灰度、成本/token。

## Phase 12 · 评估闭环 `obs/judge.py` `obs/evaluate.py`

**目标**：结论质量打分 + 历史案件离线回归 + 人工裁决回流。

**前置**：Phase 11。

**要写**
- `obs/judge.py`：LLM-as-judge 三维（有无条款依据 / 金额是否算对 / 拒赔理由是否充分），分数写回对应 trace。
- `obs/evaluate.py`：把 A~E 做成 dataset，`experiment` 跑基线；改免赔额 1 万→1.5 万重跑，输出对比报告（Case A 应赔应从 0.8 万变 0.3 万）。
- （进阶）annotation queue：把 HITL 核赔员裁决回流为标注。

**自测**：回归报告能反映规则变更对结论的影响；judge 分数出现在 trace 上。

**复习点**：LLM-as-judge、dataset/experiment、标注队列。

## 推进方式建议

1. 一次只做一个 Phase，做完跑"自测方法"，通过再进下一个。
2. 始终先保证 `core/`（业务层）能独立跑，再叠 `obs/`（观测层）——**观测不侵入业务**是这个项目的灵魂。
3. 每个 Phase 我给实现、你验证；卡住了就把自测输出贴出来一起排查。

准备好从 **Phase 0** 开始时告诉我，我就带你落地第一步。
