## 1. 分层与依赖方向

```
provider/ (项目已有：glm_model / embeddings)         ← 被 data、kb、core、obs 复用
        ▲
┌───────┴──────────────────────────────────────────────────────┐
│  data/   业务数据层（Postgres）      —— 只读写 clm_* 表          │
│  kb/     知识层（Milvus）            —— 条款库 / 历史案例库检索   │
│  core/   Agent 业务层（LangGraph）   —— 零 Langfuse，可独立运行   │  ← 依赖 data + kb + provider
│  obs/    观测层（Langfuse）          —— 叠加 trace/score，不碰 core │  ← 依赖 core（+ langfuse）
└───────────────────────────────────────────────────────────────┘
```

依赖单向向下：`obs → core → {data, kb} → provider`。**core 绝不 import obs / langfuse**，这是本项目的灵魂（NFR-6）。

## 3. 导入约定（务必遵守，否则跑不起来）

沿用你 `00_真实业务场景` 的成熟约定：**按文件路径直接运行 + 同层裸导入 + 入口做路径准备**。

- **被 import 的模块**（如 `graph.py`、`retriever.py`）：直接裸导入同层/跨层模块，如 `import state` / `from db import get_claim` / `from retriever import search_clauses`。不写路径代码。
- **被直接运行的入口文件**（`data/db.py`、`kb/ingest.py`、`core/app.py`、`obs/run.py` 等）：顶部三行准备路径——
  ```python
  import pathlib, sys
  sys.path.insert(0, str(pathlib.Path(__file__).resolve().parents[1]))  # 综合实战_保险理赔Agent 根
  import _bootstrap  # noqa: E402  # 副作用：补 provider/data/kb/core/obs 到 path + load .env
  ```
- 各层模块**基名全局唯一**（db/state/extract/…/client/pii… 无重名），四层同时在 path 上不产生 `import xxx` 歧义。
- **不使用 `__init__.py`**：这些目录是「path 条目」不是 package，与你现有约定一致。
- （可选）想让 pyright 解析裸导入，可在 `pyproject.toml` 的 pyright 配置加 `extraPaths` 指向这四个目录。

## 5. langfuse 已升 v4（4.14.4）

你选「新」，已执行 `uv add 'langfuse>=4,<5'`：**3.15.0 → 4.14.4**。升级过程与结论：

- **符号探针**：本仓所有依赖的 API 在 v4 全部存在——`get_client` / `Langfuse(mask=, environment=)` / `start_as_current_observation(as_type=, prompt=)` / `@observe(as_type=, capture_output=)` / `propagate_attributes`（公开+私有 `langfuse._client.propagation` 路径）/ `create_score` / `get_prompt` / `create_prompt` / `CallbackHandler` / `Evaluation` / `ChatPromptClient`。→ **埋点规范.md（按 v3 写法）在 v4 完全有效，无需改写。**
- **唯一 break**：`provider/langfuse.py` 的 `make_handler` 原来传 `CallbackHandler(metadata=…)`，v4 构造器不再收 metadata/session/tags。该函数是死代码（全仓无调用方），已改为返回干净 `CallbackHandler()`，归会话/打标签改用外层 `propagate_attributes(session_id=, tags=[])`。
- **冒烟**：`provider/langfuse`、`Langfuse实战/_bootstrap`（顶层就 `get_client()`）在 v4 下 import 全绿，`make_handler()` 调用不再报错。已有 `Langfuse实战/00_真实业务场景` 脚本不受影响。
- **v4 行为变更备忘**：v4 默认「智能 span 过滤」不再导出全部 OTel span；但 **Langfuse 原生 span 照常导出**，只影响你自己接的非 Langfuse OTel span。真需要全导出时用 `Langfuse(should_export_span=lambda s: True)`。本项目用不到。
- **`update_current_trace` / `start_span`** 在 v4 已移除，但全仓未使用。

### ⚠️ 运行前必读：SOCKS 代理坑（环境问题，非代码问题）

你环境有 `ALL_PROXY=socks5://127.0.0.1:7897`。langfuse client 在**顶层 `get_client()`** 就构造 httpx.Client，会读这个变量，而 httpx 走 SOCKS 需要 `socksio` 包，否则 import 期直接 `ImportError`。跑任何 **obs 层脚本**（顶层建 client）时二选一：

```bash
# 方案 A：临时清掉 SOCKS 代理再跑（推荐，最省事）
ALL_PROXY= python 综合实战_保险理赔Agent/obs/run.py

# 方案 B：给 httpx 装 socks 支持，一次到位
uv add 'httpx[socks]'
```

> core 层（`core/app.py`）不 import langfuse，**不受此坑影响**，可直接跑。
