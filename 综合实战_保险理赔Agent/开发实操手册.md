# 开发实操手册 · 保险理赔智能审核 Agent

> **这份手册是干什么的**：其他文档是"字典"（需求 `README`、规则 `需求规格说明书`、架构 `Agent设计`、验收 `测试用例与期望`、埋点 `Langfuse埋点规范`），本手册是**施工顺序说明书**——按 Phase 0→12 告诉你每一步打开哪个文件、做什么、做完跑什么命令、看到什么算过。
>
> **怎么用**：
> 1. 从上往下做，一次只做一个 Phase；"自测"全过才进下一个（上一阶段不过，下一阶段一定返工）。
> 2. 动手写任何文件前，**先读该文件顶部的注释**——骨架已把职责、待实现函数、要点的迷你需求写在里面，本手册不重复这些内容，只告诉你顺序和验收。
> 3. 规则细节（字段定义、判定公式、阈值）一律查 `需求规格说明书.md`（下称 SRS）；期望值一律查 `测试用例与期望.md`（下称 TEST，用例编号 U/N/E/H/O）。
> 4. 卡住了：先对照"自测"的期望输出找差异 → 再查手册末尾"卡住时查哪里"。

## Phase 0 · 环境与连通性

**目标**：Milvus、Postgres、模型、embedding 四条腿全部连通，并**记下 embedding 维度**（Phase 2 建表要用）。

**先确认现状**（`目录规划.md` §4：`pymilvus`、`langgraph-checkpoint-postgres`、langfuse v4 都已装好，不用再装）。

**步骤**
- [ ] 确认项目根 `.env` 里有：`DB_URI`（已有）、`MILVUS_URI`、`MILVUS_TOKEN`、模型与 embedding 的 key。
- [ ] 起 Milvus：本地用 docker 起 standalone（端口 19530），或用 Zilliz Cloud 拿连接串；`docker ps` 能看到 milvus 容器在跑。
- [ ] 写一个**临时脚本**（放在本目录，用完可删），做两件事：
  1. 用 pymilvus 连 Milvus，打印服务版本号（连通即算过）；
  2. 调 `provider.embeddings.embed_query("测试")`，打印返回向量的**维度**，把数字记下来（建议直接写进本手册 Phase 2 那一节：维度 = ____）。
- [ ] 顺手验证 `provider.glm_model` 能正常对话（发一句打印回复）。

**自测**
- 临时脚本一次跑通，输出包含：Milvus 版本号、一个 embedding 维度数字（千问 embedding 通常是 1024）、模型回复一句话。

## Phase 1 · 业务数据层

**目标**：五张业务表建好、五个样例案件灌好（幂等），`data/db.py` 直接跑能打印校验信息。

**改哪些文件**：`data/db.py`、`data/raw_clauses.py`（两个文件顶部的"待实现"清单就是完整任务列表）。

**步骤**
- [ ] `data/raw_clauses.py`：写两块纯数据（不含任何逻辑）：
  - `CLAUSES` 条款语料：至少覆盖 SRS 要求的 5 个 category（报销比例 / 免赔额 / 除外责任 / 等待期 / 保障范围），每类 1~2 条，每条带 `clause_no / product / category / text`；**免赔额 10000、有社保比例 100%、等待期 30 天、既往症除外**的数字/口径必须和 SRS §0 术语表一致（下游测算要引用它）。
  - `FRAUD_CASES` 历史案例语料：`case_no / product / summary / label`；**必须有一条与 Case E 情节高度相似的"欺诈"案例**（否则 Phase 6 的相似检索到不了 score≥0.8，TEST U-4a 会挂），再配几条"正常"案例做对照。
- [ ] `data/db.py` 第一步——建表：按 `README.md` §5.1 的五张表（+可选 `clm_fraud_watch`）逐字段写 ORM，字段名/类型/含义照抄表格，每个字段加中文注释；风格对齐 `provider/ecommerce.py`。
- [ ] `data/db.py` 第二步——种子数据 `seed()`，把 A~E 造出来，**每个案件的数据必须能推出 TEST §L3 的期望**：
  - Case A：住院 28000 / 社保 10000 / 材料齐 / 过等待期 / 非既往症 → 手算应赔 8000；
  - Case B：住院 180000 / 社保 50000 → 手算应赔 120000；
  - Case C：出险日期落在 `effective_date + 30 天` 之内（等待期）；
  - Case D：材料里**故意不放"费用清单"**，其余齐全；
  - Case E：给同一被保险人造**2 条已结案历史**（都在 90 天内）+ 就诊医院放进 `clm_fraud_watch` 名单。
- [ ] `data/db.py` 第三步——幂等：`init_db()` 用 `create_all`；`seed()` 里每条种子先 `session.get` 查主键、存在就跳过；整个文件反复执行不产生重复行。
- [ ] `data/db.py` 第四步——查询函数 7 个（名单见文件头"待实现"：get_claim / get_policy / get_insured / list_materials / count_recent_claims / hit_fraud_watch / finalize_claim），**返回纯 dict**，不外泄 ORM 对象。
- [ ] `data/db.py` 第五步——文件底部加 `__main__` 自测入口（照文件头注释的路径准备三行写）。

**自测**
```bash
python data/db.py        # 跑两遍，验证幂等
```
- 两遍输出完全一致：各表行数正确（案件 5、材料 ≥ 15、E 的历史 2 条…）；
- 5 个案件概览打印出来，A 旁标注手算 8000、B 标注 120000，和种子数据对得上。

## Phase 2 · Milvus 知识层

**目标**：两个 collection（条款库 / 历史案例库）建好灌好，能带 metadata 过滤检索。

**改哪些文件**：`kb/milvus_store.py` → `kb/ingest.py` → `kb/retriever.py`（按这个顺序写，前一个是后一的地基）。

**步骤**
- [ ] `milvus_store.py`：按文件头实现 4 个函数（get_client / ensure_collection / upsert / search）。要点：向量维度用 Phase 0 记下的数字；度量 `COSINE`；索引 `HNSW`；`product / category / clause_no / label` 建成 scalar 字段，`search` 的 `expr` 参数用来拼过滤条件。
- [ ] `ingest.py`：`main()` 读 `raw_clauses` → 逐条 `embeddings.embed_query`（条款 embed `text`，案例 embed `summary`）→ 组装行 → upsert 进两个 collection。幂等二选一：按业务主键去重，或加 `--recreate` 开关先 drop 再建。
- [ ] `retriever.py`：按文件头实现 2 个业务检索函数（search_clauses / search_similar_cases）。要点：查询文本先 embed 再 search；检索为空/超时**返回 `[]` 不抛异常**（降级判断留给节点）。

**自测**（灌库 + 三组检索断言，对应 TEST U-3 / U-4）
```bash
python kb/ingest.py
```
- U-3a：查"住院费用免赔额如何计算"（product=医疗险）→ top1 的 `category=="免赔额"`；
- U-3b：同查询但 product=意外险 → 不返回医疗险条款；
- U-3c：乱码查询 → 返回空或低分，不报错；
- U-4a：用 Case E 的案情摘要查相似案例 → top1 `label∈{欺诈,存疑}` 且 `score≥0.8`（**到不了 0.8 就回 Phase 1 改 FRAUD_CASES 的措辞**，让欺诈案例 summary 和 Case E 情节更像）。

## Phase 8 · HITL 人工核赔 + 持久化

**目标**：转人工案件在核赔节点中断，四种裁决都能 resume；进程重启后能续跑。

**改哪些文件**：`core/human_review.py`、`core/graph.py`、`core/app.py`。

**步骤**
- [ ] `human_review.py`：调 `interrupt(证据包)`——载荷按 AC-9.1 组装（应赔额 + Settlement 明细 + clause_evidence + fraud.signals + 关键抽取字段）；resume 拿到 `AdjusterAction` 后校验载荷，按 approve / adjust / reject / return 四动作更新 state 并返回 Command 路由（approve→出具通过、adjust→按核赔员金额并记差异事件、reject→拒赔、return→回 need_more）。
- [ ] `graph.py`：`build_graph` 增加 `checkpointer` / `store` 参数；`compile(checkpointer=PostgresSaver(...))`，用 `DB_URI` 连接；thread_id = claim_id。PostgresSaver 首次使用要执行 `setup()` 建检查点表。
- [ ] `app.py`：演示脚本改成两段式——先 invoke（拿到 `__interrupt__` 打印证据包），再用 `Command(resume=...)` 注入裁决续跑。

**自测**（对应 TEST §L4）
- E-B：invoke 后停在 interrupt，打印出的载荷里 payable=120000 + 明细 + 条款 + 风险齐全；
- H-1 approve → 按 120000 结案，status=已赔付，事件 actor=ADJ1；
- H-2 adjust(100000) → approved_amount=100000，记"差异 -20000"事件；
- H-3 reject → status=已拒赔，文书含核赔员理由；
- H-4 return → 回 need_more，status=待补件；
- H-5 重启验证：跑 B 到 interrupt 后 Ctrl-C 杀掉进程，重开进程用同一 claim_id invoke → 从中断点继续，不重跑前面节点。
