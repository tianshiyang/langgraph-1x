# 快速开始 — 知识点总结与扩展

> 基于 `官方文档/快速开始/index.py` 示例，对涉及的 LangGraph 核心概念进行总结和扩展。

---

## 一、整体架构

这个示例构建了一个**工具调用 Agent**，整体流程如下：

```
用户输入 → LLM 判断是否需要调用工具
              ├── 需要调用 → 执行工具 → 再回到 LLM（循环）
              └── 不需要   → 直接输出结果 → 结束
```

对应的图结构：

```
START ──→ llm_call ──→ (需要工具?) ──→ tool_node ──→ llm_call (循环)
                         │
                         └──→ (不需要) ──→ END
```

## 二、核心知识点

### 2.1 工具定义（@tool 装饰器）

```python
from langchain_core.tools import tool

@tool
def multiply(a: int, b: int) -> int:
    """计算两个数的乘积"""
    return a * b
```

**要点：**

- `@tool` 装饰器将普通 Python 函数转换为 LangChain 工具
- 函数的 **docstring** 非常重要 — LLM 通过它来理解工具的用途，决定是否调用
- 函数的**参数类型注解**同样重要 — LLM 据此知道该传什么类型的参数
- `bind_tools(tools)` 将工具绑定到模型上，让模型"知道"自己可以调用哪些工具

**工具注册表模式：**

```python
tools_by_name = {tool.name: tool for tool in tools}
```

这是一个常见的字典映射模式，方便在 `tool_node` 中通过工具名快速查找对应的工具函数。

### 2.2 状态定义（MessagesState）

```python
class MessagesState(TypedDict):
    messages: Annotated[list[AnyMessage], operator.add]
    llm_calls: int
```

**要点：**

- `TypedDict` 定义了图的状态结构，所有节点共享这个状态
- `Annotated[list[AnyMessage], operator.add]` 中的 `operator.add` 是**状态更新策略（reducer）**
  - 默认行为是**覆盖**：节点返回什么，状态就变成什么
  - 使用 `operator.add` 后变成**追加**：节点返回的新消息会追加到已有消息列表中
- `llm_calls: int` 没有指定 reducer，所以默认是覆盖行为

> **为什么不直接覆盖 messages？**
>
> 因为在多节点的图中，每个节点可能只产生**一条新消息**。如果直接覆盖，之前的对话历史就丢失了。
> 使用 `operator.add` 相当于：`新状态 = 旧消息 + 本节点返回的消息`，对话历史会自动累积。

### 2.3 节点（Node）

#### llm_call 节点 — LLM 决策

```python
def llm_call(state: MessagesState):
    return {
        "messages": [
            model_with_tools.invoke(
                [SystemMessage(content="您是一位有用的助手...")]
                + state["messages"]
            ),
        ],
        "llm_calls": state.get("llm_calls", 0) + 1,
    }
```

**要点：**

- `[SystemMessage(...)] + state["messages"]`：把系统提示词和完整对话历史拼在一起，传给 LLM
  - 这里的 `+` 是 Python 列表拼接，**不是** LangGraph 的 `operator.add`
  - 如果不加 `state["messages"]`，LLM 就看不到用户消息和之前的对话，无法做出正确判断
- 节点**必须返回一个字典**，key 要和 `MessagesState` 的字段名对应
- 返回的 `"messages"` 是一个只包含**本次新产生消息**的列表，LangGraph 会自动用 `operator.add` 追加到已有状态中

#### tool_node 节点 — 执行工具

```python
def tool_node(state: MessagesState):
    result = []
    for tool_call in state["messages"][-1].tool_calls:
        tool = tools_by_name[tool_call["name"]]
        observation = tool.invoke(tool_call["args"])
        result.append(ToolMessage(content=observation, tool_call_id=tool_call["id"]))
    return {"messages": result}
```

**要点：**

- `state["messages"][-1]` 取最后一条消息，即 LLM 的回复（AIMessage），其中包含 `tool_calls` 信息
- 每个 `tool_call` 包含工具名（`name`）和参数（`args`）
- 返回的 `ToolMessage` 必须携带 `tool_call_id`，用于关联到 LLM 发起的那个工具调用
- LLM 一次可能会发起**多个工具调用**，所以用 `for` 循环逐个执行

### 2.4 条件边（Conditional Edge）

```python
def should_continue(state: MessagesState) -> Literal["tool_node", END]:
    messages = state["messages"]
    last_message = messages[-1]
    if last_message.tool_calls:
        return "tool_node"
    return END

agent_builder.add_conditional_edges("llm_call", should_continue, ["tool_node", END])
```

**要点：**

- 条件边根据状态**动态决定**下一步走哪条路径
- `should_continue` 检查 LLM 的回复中是否包含 `tool_calls`
  - 有 `tool_calls` → 路由到 `tool_node` 继续执行
  - 没有 `tool_calls` → 走到 `END` 结束
- `add_conditional_edges` 的第三个参数 `["tool_node", END]` 是所有可能的返回值，用于图的构建和可视化

### 2.5 图的构建流程

```python
agent_builder = StateGraph(MessagesState)        # 1. 用状态类创建图
agent_builder.add_node("llm_call", llm_call)     # 2. 添加节点
agent_builder.add_node("tool_node", tool_node)
agent_builder.add_edge(START, "llm_call")                    # 3. 固定边
agent_builder.add_conditional_edges("llm_call", should_continue, ...)  # 4. 条件边
agent_builder.add_edge("tool_node", "llm_call")              # 5. 循环边
agent = agent_builder.compile()                   # 6. 编译
```

**要点：**

- `START` 和 `END` 是 LangGraph 的内置常量，分别表示图的入口和出口
- `add_edge("tool_node", "llm_call")` 构成了一个**循环**，让工具执行后可以回到 LLM 继续判断
- 整个 Agent 就是一个 `llm_call ↔ tool_node` 的循环，直到 LLM 不再调用工具为止

## 三、消息类型详解

LangChain 定义了多种消息类型，每种都有特定的角色和用途：

### 3.1 SystemMessage — 系统消息

**角色：** 设定 AI 的行为、人设、规则等。

```python
from langchain_core.messages import SystemMessage

SystemMessage(content="您是一位有用的助手，负责对一组输入执行算术运算。")
```

- 通常放在对话的**最前面**
- 对用户不可见，但对 LLM 的行为有重大影响
- 每次调用 LLM 时都会重新传入（因为它不在 `state["messages"]` 里，而是在节点函数里手动拼接的）

### 3.2 HumanMessage — 用户消息

**角色：** 用户发送的消息，即"人说的话"。

```python
from langchain_core.messages import HumanMessage

HumanMessage(content="Add 3 and 4.")
```

- 是整个对话的**起点**
- 通常在 `agent.invoke()` 时作为初始输入传入

### 3.3 AIMessage — AI 消息

**角色：** LLM 返回的消息，即"模型的回复"。

```python
# 普通回复
AIMessage(content="3 + 4 = 7")

# 带工具调用的回复
AIMessage(
    content="",
    tool_calls=[
        {
            "name": "add",
            "args": {"a": 3, "b": 4},
            "id": "call_abc123"
        }
    ]
)
```

- 当 LLM 认为需要调用工具时，`content` 可能为空，转而在 `tool_calls` 中携带工具调用信息
- `tool_calls` 是一个列表（LLM 可能一次发起多个工具调用）
- 每个 tool_call 包含三个字段：
  - `name`：要调用的工具名
  - `args`：传给工具的参数
  - `id`：唯一标识，用于后续关联 `ToolMessage`

### 3.4 ToolMessage — 工具消息

**角色：** 工具执行后返回的结果。

```python
from langchain_core.messages import ToolMessage

ToolMessage(content="7", tool_call_id="call_abc123")
```

- `tool_call_id` 是关键字段，**必须**与 `AIMessage.tool_calls` 中的 `id` 对应
- `content` 是工具的返回值（会转为字符串）
- LLM 通过 `tool_call_id` 知道这个结果是哪个工具调用的返回值

### 3.5 AnyMessage — 联合类型

```python
from langchain_core.messages import AnyMessage
```

`AnyMessage` 是上述所有消息类型的**联合类型**（Union），用于类型注解中，表示"任意类型的消息都可以"。

## 四、真实对话场景中的消息结构

以用户提问 `"3加4再乘以5等于多少？"` 为例，LLM 需要先调用 `add` 再调用 `multiply`。

### 4.1 消息流转过程

```
轮次1: 用户提问
  [HumanMessage("3加4再乘以5等于多少？")]

轮次2: LLM 决定先算加法
  [AIMessage(tool_calls=[{name: "add", args: {a:3, b:4}, id: "call_001"}])]

轮次3: 工具返回加法结果
  [ToolMessage(content="7", tool_call_id="call_001")]

轮次4: LLM 拿到加法结果，决定再算乘法
  [AIMessage(tool_calls=[{name: "multiply", args: {a:7, b:5}, id: "call_002"}])]

轮次5: 工具返回乘法结果
  [ToolMessage(content="35", tool_call_id="call_002")]

轮次6: LLM 拿到最终结果，直接回答
  [AIMessage(content="3加4再乘以5等于35。")]
```

### 4.2 完整的 messages 列表

最终 `state["messages"]` 的完整内容如下：

```python
[
    # 1️⃣ 用户消息 — 对话的起点
    HumanMessage(content="3加4再乘以5等于多少？"),

    # 2️⃣ AI 消息 — LLM 决定调用 add 工具
    AIMessage(
        content="",
        tool_calls=[
            {
                "name": "add",
                "args": {"a": 3, "b": 4},
                "id": "call_001",
                "type": "tool_call"
            }
        ]
    ),

    # 3️⃣ 工具消息 — add(3, 4) 的返回值
    ToolMessage(
        content="7",
        tool_call_id="call_001"
    ),

    # 4️⃣ AI 消息 — LLM 拿到 7，决定调用 multiply 工具
    AIMessage(
        content="",
        tool_calls=[
            {
                "name": "multiply",
                "args": {"a": 7, "b": 5},
                "id": "call_002",
                "type": "tool_call"
            }
        ]
    ),

    # 5️⃣ 工具消息 — multiply(7, 5) 的返回值
    ToolMessage(
        content="35",
        tool_call_id="call_002"
    ),

    # 6️⃣ AI 消息 — LLM 给出最终回答
    AIMessage(
        content="3加4再乘以5等于35。"
    ),
]
```

### 4.3 每轮 LLM 调用时收到的完整输入

注意：`SystemMessage` 不在 `state["messages"]` 中，而是在 `llm_call` 节点里手动拼接的。所以每轮 LLM 实际收到的输入是这样的：

**第 1 轮调用（收到用户消息后）：**

```python
[SystemMessage("您是一位有用的助手..."), HumanMessage("3加4再乘以5等于多少？")]
```

**第 2 轮调用（add 工具执行后）：**

```python
[
    SystemMessage("您是一位有用的助手..."),
    HumanMessage("3加4再乘以5等于多少？"),
    AIMessage(tool_calls=[...add...]),
    ToolMessage(content="7", tool_call_id="call_001"),
]
```

**第 3 轮调用（multiply 工具执行后）：**

```python
[
    SystemMessage("您是一位有用的助手..."),
    HumanMessage("3加4再乘以5等于多少？"),
    AIMessage(tool_calls=[...add...]),
    ToolMessage(content="7", tool_call_id="call_001"),
    AIMessage(tool_calls=[...multiply...]),
    ToolMessage(content="35", tool_call_id="call_002"),
]
```

> 可以看到，随着对话进行，传给 LLM 的消息列表会**越来越长**。这也是为什么长对话会消耗更多 token。

## 五、关键概念对比

### operator.add vs 列表拼接

| 对比项 | 状态定义中的 `operator.add` | 函数内的 `+ state["messages"]` |
|--------|---------------------------|-------------------------------|
| **作用** | LangGraph 的状态更新策略 | Python 列表拼接 |
| **场景** | 写：节点返回后，LangGraph 自动合并状态 | 读：构造传给 LLM 的完整输入 |
| **不加会怎样** | 新消息会覆盖旧消息，对话历史丢失 | LLM 看不到对话内容，无法正确回答 |

### 节点 vs 边

| 对比项 | 节点（Node） | 边（Edge） |
|--------|-------------|-----------|
| **作用** | 执行具体的逻辑（调 LLM、执行工具等） | 决定流程的走向 |
| **类型** | 普通边、条件边 | — |
| **返回值** | 状态更新字典 | 下一个节点名称 |

## 六、扩展知识

### 6.1 LangGraph 内置的 MessagesState

LangGraph 其实提供了一个内置的 `MessagesState`，已经帮你定义好了 `messages` 字段：

```python
from langgraph.graph import MessagesState

# 等价于你自己定义的：
# class MessagesState(TypedDict):
#     messages: Annotated[list[AnyMessage], operator.add]
```

所以示例中的自定义 `MessagesState` 额外加了 `llm_calls` 字段。如果不需要这个字段，可以直接用内置的。

### 6.2 为什么需要 ToolMessage 的 tool_call_id

LLM 可能一次发起多个工具调用，例如：

```python
AIMessage(
    tool_calls=[
        {"name": "add", "args": {"a": 1, "b": 2}, "id": "call_001"},
        {"name": "multiply", "args": {"a": 3, "b": 4}, "id": "call_002"},
    ]
)
```

这时需要返回两个 `ToolMessage`，每个都要带上对应的 `tool_call_id`：

```python
ToolMessage(content="3", tool_call_id="call_001")
ToolMessage(content="12", tool_call_id="call_002")
```

这样 LLM 才能正确地将工具结果和对应的调用关联起来。

### 6.3 多轮对话中的 token 消耗

从上面的消息结构可以看出，每经过一轮 `llm_call → tool_node → llm_call` 循环，传给 LLM 的消息列表就会增长。如果循环次数很多，token 消耗会快速增长。在实际生产中，通常需要考虑：

- 设置最大循环次数限制
- 使用消息截断或摘要策略
- 监控 `llm_calls` 计数来控制成本
